## 2. Posture summary
The read-only core holds:

- **Route allowlist and gwmcloud live gate:** no bypass under URL-normalization variants.
- **TLS:** always verified, including inside the CONNECT tunnel. The client certificate is presented only when it is configured.
- **Secrets:** file-only intake, central redaction, and a 0600/0700 state file.
- **Session:** the login cap and the halt work as designed.
- **Containers:** isolated.
- **CI:** read-only.

The confirmed defects sit at the edges:

- **Broker:** client ids are not bound to users.
- **Egress proxy:** the reverse-DNS match lets an IP literal through.
- **Two unbounded or unescaped GWM-controlled strings:** one blocks the event loop, one reaches the HA markdown card.
- **Fork lifecycle:** upstream workflows reach the fork's branches.

No finding gives vehicle control, credential disclosure or remote code execution.

### 3.1 A read-only MQTT user can take over the reader's fixed client id and make the broker write a retained offline availability to gwmbrasil/#, bypassing the topic ACL

- **Fingerprint:** `mosquitto/mosquitto.conf:clientid-takeover-will:haval-h6-mqtt/mqtt.js:createPublisher`
- **Severity:** medium. Likelihood medium: No write permission is needed: any party holding the homeassistant or kinestra_bridge password, or who compromises Home Assistant (a large third-party app) or the kinestra bridge, can run a one-line CONNECT with a known, deterministic client id. The exact client id is derivable from VEHICLE_ID (gwm-reader-h6 by default). It does require an authenticated foothold on the internal broker, which bounds the likelihood below high. Impact medium: A read-only user bypasses the topic ACL to write a retained value to gwmbrasil/#, driving a persistent false offline that makes Home Assistant mark every gwmbrasil entity unavailable while state topics keep updating; the stale retained value survives until the reader process restarts. The same move repeatedly disconnects the reader's broker session (availability/monitoring denial of service). It does not disclose secrets, does not forge vehicle state values, and grants no vehicle control, bounding impact below high.
- **Source location:** `mosquitto/acl:13` (entrypoint); `mosquitto/mosquitto.conf:8` (propagation); `haval-h6-mqtt/mqtt.js:117` (propagation); `haval-h6-mqtt/mqtt.js:124` (propagation); `haval-h6-mqtt/reader.js:83` (sink)
- **Lower-trust principal:** An authenticated read-only MQTT peer (homeassistant or kinestra_bridge) that has no write permission on gwmbrasil/# and wants to write a retained value there and/or disrupt the reader.
- **Conditions:** [authentication_level] The actor is an authenticated MQTT user of the broker (holds the homeassistant or kinestra_bridge password, or has compromised Home Assistant or the kinestra bridge, both authenticated peers of mosquitto:1883). [authorization_role] The actor's ACL role is read-only on gwmbrasil/# (no write rule), so the resulting retained write is outside its granted authority. [system_configuration] mosquitto/mosquitto.conf does not set use_username_as_clientid (or any client-id-to-username binding), so the broker accepts another user's CONNECT bearing the reader's client id. [third_party_dependency] Mosquitto 2.1.2 performs MQTT v5 session takeover on a duplicate client id and publishes the taken-over session's retained will (no will-delay), observed directly with the pinned broker image.
- **Bounded reproduction:** Start the pinned eclipse-mosquitto:2.1.2-alpine broker with the repository mosquitto.conf (only password_file/acl_file/persistence paths rewritten to tmpfs/read-only mounts) and the repository acl verbatim, in an isolated network namespace. Connect the real reader via createPublisher() as gwm_reader with vehicleId h6 and publish online retained to gwmbrasil/h6/availability. As homeassistant, attempt a direct retained publish of offline to gwmbrasil/h6/availability and observe it is refused Not authorized. As homeassistant, open a CONNECT with clientId gwm-reader-h6 and clean start (no will); wait briefly, then read the retained gwmbrasil/h6/availability as homeassistant. Disconnect the attacker and read the retained value again; repeat the sequence as kinestra_bridge.
- **Actual result:** The direct retained publish was refused (Not authorized), confirming the topic ACL. The CONNECT bearing clientId gwm-reader-h6 was accepted (connack 0) for both homeassistant and kinestra_bridge; the broker logged 'Client gwm-reader-h6 ... disconnected: session taken over' and a new client 'gwm-reader-h6 ... u'homeassistant''/'u'kinestra_bridge''. The retained gwmbrasil/h6/availability read back as 'offline' while the read-only user held the id and remained 'offline' after it disconnected; it returned to 'online' only after an explicit reader re-publish (which the production reader does not perform on reconnect). Evidence: agents/v3-mosquitto/artifacts/check-1.txt (probe), agents/v3-mosquitto/artifacts/check-2.txt (broker log).
- **Root cause:** Broker authority over a client id is not tied to the authenticated user (mosquitto/mosquitto.conf has no use_username_as_clientid or equivalent), so any authenticated user can present the reader's deterministic client id. Combined with the reader's predictable client id plus a retained will (haval-h6-mqtt/mqtt.js:116-123) and the absence of any online re-publish on reconnect (haval-h6-mqtt/reader.js:83; no connect handler at haval-h6-mqtt/mqtt.js:124-125), a takeover by a read-only user writes and leaves a retained offline on a topic that user's ACL forbids.
- **Smallest fix:** Bind client-id ownership to the authenticated user at the broker and make the reader self-heal its availability. In mosquitto/mosquitto.conf set use_username_as_clientid true so the broker forces each connection's effective client id to its username; a read-only user can then never present gwm-reader-<VEHICLE_ID>, so it cannot take over the reader's session or trigger its will. Independently, defend in depth in the reader: register a client.on('connect') handler that re-publishes availability online retained on every (re)connection, so a transient drop or takeover does not leave a stale retained offline. Keeping both closes the ACL bypass and the persistence of a false unavailable state.

### 3.2 GWM tire-temperature value injects markdown and forged records into status_message, which the shipped HA markdown card renders

- **Fingerprint:** `haval-h6-mqtt/carTextUtil.js:status_message:unescaped-gwm-value-in-pipe-delimited-markdown`
- **Severity:** low. Likelihood low: The value must come from the GWM cloud itself, or from a party trusted for its TLS host, and the owner must use the shipped dashboard. Impact low: Content spoofing with a phishing link and a remote-image beacon in the owner's own HA UI. There is no script execution, credential access, MQTT topic control or vehicle effect.
- **Source location:** `haval-h6-mqtt/carConnector.js:258` (entrypoint); `haval-h6-mqtt/reader.js:41` (propagation); `haval-h6-mqtt/carTextUtil.js:109` (propagation); `haval-h6-mqtt/carTextUtil.js:36` (propagation); `haval-h6-mqtt/reader.js:228` (propagation); `ha/dashboard.yaml:861` (propagation); `ha/dashboard.yaml:893` (sink)
- **Lower-trust principal:** A lower-trust GWM API endpoint that returns a well-formed getLastStatus response.
- **Conditions:** [third_party_dependency] The GWM API, or a party trusted for its TLS host, returns the crafted temperature value. Home Assistant's markdown card renders markdown links and images. The HA frontend sanitizer, any CSP, and the 255-character state limit are outside this repository and bound the payload to links and images, not script. The observed payloads are 159-179 characters. [system_configuration] The owner has installed the shipped ha/dashboard.yaml. [data_state] Status includes window item 2210001 (any value, so the analysis runs), a front-right pressure outside 35-39 psi, and the temperature item 2101006. GWM controls all of these. [user_interaction] The owner opens the dashboard, which loads remote images. A phishing link needs a click.
- **Bounded reproduction:** In a no-network, read-only container, build the real GwmClient and Reader with an in-memory http.request stub (a successful login, one vehicle with a dummy VIN, and the payload as getLastStatus) and an in-memory publisher. Run Reader.pollStatus() once. Read the retained payload published to gwmbrasil/h6/status_message/state, and apply the branch selection of ha/dashboard.yaml:858-899 (split on '|', then on '@').
- **Actual result:** agents/v1-havalh6mqtt/artifacts/check-1.txt: V1_pipe 'topic=gwmbrasil/h6/status_message/state retain=true len=179' and dashboard_branches 'TIRE_PRESSURE partes[3]="20 "', 'ELSE item=" [Atualize sua conta GWM](https://example.invalid/login) ![](https://example.invalid/p.png)°C "', 'TIRE_PRESSURE_DEFAULTS'. V2_nopipe (no '|') 'TIRE_PRESSURE partes[3]="20 [Atualize](https://example.invalid/l) ![](https://example.invalid/b.png)°C "'. V3 control with numeric '20' gives 'TIRE_PRESSURE partes[3]="20°C "'. The HA markdown rendering itself was not executed.
- **Root cause:** getVehicleStatusHardAnalysis interpolates the GWM tire-temperature value into a delimiter-based record format without a numeric check and without escaping '@', '|', newlines or markdown (carTextUtil.js:35-36,109,136; reader.js:228). The shipped dashboard renders the parsed parts, and any unknown record, as markdown without escaping or validation (ha/dashboard.yaml:856,861,893,899 and 1530,1535,1567,1573).
- **Smallest fix:** Accept only finite numeric values for the tire temperature, and validate every other value placed in status_message. Strip '|', '@', CR and LF from any value placed in status_message. In the dashboard, remove the raw '{{ item }}' fallback and reduce partes[n] to a safe character set before rendering. Add a reader test in which a temperature with '|' and markdown yields exactly one TIRE_PRESSURE record with a placeholder value.

### 3.3 Unbounded GWM body.code drives quadratic regex backtracking in redactString and blocks the reader event loop

- **Fingerprint:** `haval-h6-mqtt/logger.js:redactString:quadratic-regex-on-unbounded-gwm-api-code`
- **Severity:** low. Likelihood low: The input must come from the GWM cloud itself or a party trusted by the TLS-verified client for the GWM host (or an owner-chosen fixture host). A network attacker without a trusted certificate cannot inject it. Impact low: One response stalls the single-owner reader and burns its 0.5 CPU share for hours, and the LWT makes every HA entity unavailable until the owner restarts the container. No data, credential or vehicle control is exposed, and the GWM cloud could already withhold or falsify status data.
- **Source location:** `haval-h6-mqtt/httpClient.js:151` (entrypoint); `haval-h6-mqtt/carConnector.js:150` (propagation); `haval-h6-mqtt/carConnector.js:256` (propagation); `haval-h6-mqtt/carConnector.js:227` (propagation); `haval-h6-mqtt/reader.js:185` (propagation); `haval-h6-mqtt/logger.js:144` (propagation); `haval-h6-mqtt/logger.js:83` (sink)
- **Lower-trust principal:** A lower-trust GWM API endpoint that returns a well-formed 2xx JSON envelope with an oversized code string to a status poll.
- **Conditions:** [third_party_dependency] The GWM API endpoint, or a party that presents a certificate trusted for that host (system roots plus an optional GWM_EXTRA_CA_FILE), returns the hostile envelope. In fixture mode, the owner-configured fixture host can do the same. [data_state] A vehicle endpoint (getLastStatus on every poll, acquireVehicles, or getChargeLogs) returns HTTP 2xx with description != SUCCESS, null data, and a long string code that is not in AUTH_CODES, RATE_LIMIT_CODES or BUSY_CODES. [system_configuration] Live mode is enabled (GWM_LIVE_ENABLED=true) with a valid session, or fixture mode points at a lower-trust host; LOG_LEVEL is WARN, INFO or DEBUG (the compose default is INFO), so the poll-failed warning is emitted.
- **Bounded reproduction:** In a no-network container (node:24.22.0-alpine3.23, 0.5 CPU, 256 MiB, read-only target), require haval-h6-mqtt/logger.js and time redactString on the error_class shape for each n (check-1). Build the real GwmClient and Reader with an in-memory http.request stub: loginAccount returns SUCCESS with a dummy JWT, acquireVehicles returns one dummy vehicle, and getLastStatus returns the payload. Use the real createLogger and an in-memory publisher. Time Reader.pollStatus for each n and read the retained reader_error attributes (check-2). Start eclipse-mosquitto 2.1.2 with --network none and default local-only config, a mosquitto_sub on gwmbrasil/h6/availability and gwmbrasil/h6/reader_error/#, and a reader process in the same loopback namespace that uses the real createPublisher (keepalive lowered to 5 s through the injectable connect, only to fit the wall clock). Publish 'online', run one pollStatus with n = 64000, and record broker, subscriber and event-loop gap output (check-3).
- **Actual result:** check-1 (agents/v2-havalh6mqtt/artifacts/check-1.txt): redactString api_+a*n ms = 114.43 / 421.86 / 1659.39 / 6703.96 / 26600.54 for n = 4000..64000 (linear baseline 0.70-13.40 ms); EMAIL alone at 64000 = 25596.38 ms, EMAIL with a {1,64} bound = 167.65 ms. check-2 (agents/v2-havalh6mqtt/artifacts/check-2.txt): 'getLastStatus code_len=64000 pollStatus_ms=26896.9 ... reader_error_retain=true error_class_len=64004', 4x per doubling, with http_calls [loginAccount, acquireVehicles, getLastStatus] and logins 1. check-3 (agents/v2-havalh6mqtt/artifacts/check-3.txt): reader 'max_event_loop_gap_ms=28009'; broker '1792678780: Client gwm-reader-h6 [127.0.0.1:45120] disconnected: exceeded timeout.'; subscriber '[1792678780] SUB gwmbrasil/h6/availability offline', then at 1792678806 'reader_error/state retrying' and attributes with the raw 'api_aaaa...' error_class; no 'online' was published after the reconnect. The duration at the 4 MiB cap (about 30 h) is extrapolated from the observed quadratic curve, not executed.
- **Root cause:** parse() accepts body.code of any length and shape (carConnector.js:150), unlike the 200-char slice in toGwmError (httpClient.js:173), and requireData puts it in errorClass (carConnector.js:227). redactString then runs regexes with unbounded greedy quantifiers and no anchors over the full string, with no input-size cap (logger.js:18,20,25,76-88).
- **Smallest fix:** Validate GWM API codes in parse() as short tokens and replace any other value with a constant, so error classes, logs and retained attributes stay bounded. In logger.js, bound every regex quantifier and cap redactString input to a fixed length after the exact-secret pass, cutting back to a non-token character with a linear scan (not a regex). Optionally publish 'online' again on every MQTT connect. Add regression tests: redactString("a".repeat(1 << 20)) and a Reader poll whose getLastStatus code is 1 MiB both finish in well under 100 ms, and error_class in reader_error attributes is at most 20 chars.

### 3.4 Squid dstdomain allowlist without -n accepts CONNECT to an IP literal whose reverse DNS name matches an allowlisted host

- **Fingerprint:** `proxy/squid.conf:acl-allowlist-dstdomain-rdns-ip-literal-connect`
- **Severity:** low. Likelihood low: Exploitation requires a compromise of a reader dependency or of a container attached to mqtt_internal, which this egress control is the last line against, plus control of an internet IP's PTR record, which many hosting providers allow. No other barrier exists once those hold. Impact medium: It defeats the egress allowlist, the control meant to stop a compromised reader from sending tokens, the device id, the VIN and coordinates anywhere but GWM; it gives an arbitrary port-443 TCP tunnel to an attacker IP. It gives no access by itself, and the attacker must already run code inside the stack.
- **Source location:** `proxy/squid.conf:14` (entrypoint); `docker-compose.yml:69` (propagation); `proxy/squid.conf:11` (propagation); `proxy/squid.conf:17` (sink)
- **Lower-trust principal:** Code running in a container on mqtt_internal (RFC1918 source) that wants to reach an arbitrary internet IP on port 443 through the allowlisting Squid proxy.
- **Conditions:** [network_routing] The attacker needs code running on a container attached to mqtt_internal (for example a compromised dependency in the reader, which has no other route out, or another attached container) to reach squid:3128. [third_party_dependency] The attacker needs an internet IP reachable on 443 whose reverse DNS (PTR) record they control and set to an allowlisted name; Squid does no forward-confirmation of the PTR name. [system_configuration] The deployed allowlist (gitignored proxy/allowlist.local.txt) holds host names, and the deployed squid resolves PTR queries through the Docker embedded DNS and host resolvers on the egress network. The local run used a fake resolver via a harness-only dns_nameservers line. [authentication_level] No proxy authentication is configured; source address in RFC1918 is the only client check.
- **Bounded reproduction:** Start a node:24.22.0-alpine container with --network none, --read-only, --cap-drop ALL, no-new-privileges, 256m memory, 0.5 CPU, 64 pids, that runs a fake DNS on 127.0.0.1:53 (A gwm.test -> 127.0.0.5; PTR 127.0.0.5 -> gwm.test, PTR 127.0.0.6 -> evil.test) and a dummy TCP listener on :443 that writes DUMMY-443-LISTENER. Start the pinned ubuntu/squid:6.6-24.04_edge@sha256:8a3baed4... image in the same network namespace (--network container:<first>), same limits, user 13:13, tmpfs for /tmp, /var/spool/squid, /run, with proxy/squid.conf mounted read-only at /etc/squid/squid.conf and an allowlist containing only 'gwm.test' at /etc/squid/allowlist.txt. Run squid -N -f with a harness wrapper that adds 'acl localnet src 127.0.0.2/32' (the network-none namespace has no RFC1918 address; Squid ACL values accumulate), then 'include /etc/squid/squid.conf' (unmodified), 'dns_nameservers 127.0.0.1', 'visible_hostname squid-harness.test' and 'shutdown_lifetime 1 seconds'. From a third node container in the same namespace, bound to source 127.0.0.2, send CONNECT 127.0.0.5:443, 127.0.0.6:443, gwm.test:443 and 127.0.0.5:80 to 127.0.0.1:3128 and record status codes and tunnel bytes; stop squid gracefully to flush the access log; remove all containers. Repeat with 'dstdomain -n' and with an IP-literal deny rule as fix controls.
- **Actual result:** Image ubuntu/squid:6.6-24.04_edge pinned by digest sha256:8a3baed477e2c282ab8aa5edad442f69873246964f225c5c2ae8364b6610963c; the binary reports Squid 6.14. With the repository squid.conf: CONNECT 127.0.0.5:443 -> TCP_TUNNEL/200 and the tunnel returned 'DUMMY-443-LISTENER' after Squid sent a PTR query for 5.0.0.127.in-addr.arpa; CONNECT 127.0.0.6:443 (PTR evil.test) -> 403; CONNECT gwm.test:443 -> 200; CONNECT 127.0.0.5:80 -> 403. With -n or the IP-literal deny rule, CONNECT 127.0.0.5:443 -> 403 and gwm.test:443 -> 200. The destination was a loopback stand-in for an internet IP; no external network was used.
- **Root cause:** The allowlist ACL uses dstdomain without -n (proxy/squid.conf:11) and http_access has no rule that denies IP-literal CONNECT targets (proxy/squid.conf:14-18), so Squid's reverse-DNS fallback lets whoever controls an IP's PTR record make that IP match an allowlisted host name.
- **Smallest fix:** Match the allowlist only on the literal CONNECT host name: add -n to the dstdomain ACL (the tested fix, check-2). As defense in depth, deny IP-literal CONNECT targets before the allow rule (the IPv4 branch was tested in check-3; the bracketed IPv6 branch was not exercised). Add an IP-literal CONNECT case to test/integration/netprobe.js that must return 403.

## 5. Hardening notes (non-findings, from hunters)

- (h1-egress) haval-h6-mqtt/httpClient.js:79: TunnelAgent verifies the TLS name from options.servername, which Node derives from the request Host header, while the CONNECT target uses options.host (httpClient.js:64). check-1 case 10 accepted a wrong-name server when a caller set Host: other.test. No caller sets Host today (carConnector.js:21-43, 197). Bind servername to options.host and reject a caller-supplied host header in request().
- (h1-egress) haval-h6-mqtt/httpClient.js:172: toGwmError does not classify OpenSSL verify codes such as INVALID_PURPOSE as 'tls' (check-1 case 5 reported errorClass network). The request still fails closed; widen the regex so the RUNBOOK TLS triage sees it.
- (h1-egress) haval-h6-mqtt/config.js:145 and haval-h6-mqtt/httpClient.js:46: GWM_EXTRA_CA_FILE is trusted for every host, including *.gwmcloud.com in live mode. A test CA left configured (test/integration/compose.it.yml:11 uses one) would let its key holder impersonate GWM. Accept the extra CA only in fixture mode, or log a startup warning with its fingerprint in live mode.
- (h1-egress) haval-h6-mqtt/config.js:49: the live gate is a host-name suffix test. With both URLs set to IP literals or a non-gwmcloud alias, fixture mode sends the real credentials from the secret files without GWM_LIVE_ENABLED (check-2 G8). Only the owner sets these variables; consider an explicit GWM_FIXTURE=true plus refusal of non-test credentials in fixture mode.
- (h1-egress) haval-h6-mqtt/routes.js:123-130 and haval-h6-mqtt/httpClient.js:121: the guard checks the body object's own enumerable fields, but JSON.stringify honors toJSON, so the guarded and sent bodies can differ (check-2 case o). Bodies are code-built today; serialize first and guard JSON.parse(payload).
- (h1-egress) haval-h6-mqtt/httpClient.js:96 and 139: plain http: requests to non-gwmcloud hosts use a direct http.Agent and bypass HTTPS_PROXY. In the shipped compose this reaches only mqtt_internal peers (docker-compose.yml:48, 110-111); consider refusing http: unless the host is a loopback or explicitly named mock.
